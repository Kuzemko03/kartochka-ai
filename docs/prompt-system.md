# Система промптов и гейтов качества

> Тексты боевых промптов вырезаны из публичной версии репозитория — это ядро
> продукта. Здесь описано, **как устроена** система: её архитектура, этапы и
> механизмы контроля качества. Вся исполняемая логика (валидаторы, скрубберы,
> маршрутизация) осталась в коде и доступна для чтения.

Файлы: [`site/prompts.py`](../site/prompts.py) — шаблоны и валидаторы,
[`site/generator.py`](../site/generator.py) — оркестратор.

---

## Зачем это всё

Наивный подход «дай LLM фото и попроси карточку» ломается на трёх вещах:

1. **Выдуманные факты.** Модель дописывает «влагозащита IP67» товару, у которого
   её нет. Для маркетплейса это не косметика, а претензия покупателя и штраф.
2. **Одинаковость.** Пак из 5 карточек выходит пятью вариациями одного кадра.
3. **Вода в тексте.** «Качественный товар для дома» — заголовок, который не
   продаёт и не отличает от 300 конкурентов.

Ни одна из проблем не решается «промптом получше»: LLM недетерминирована, и
что-то из этого всё равно просочится. Поэтому система построена как
**конвейер с проверками на выходе каждой стадии**, а не как один большой вызов.

---

## Конвейер

```
фото + бриф
   │
   ├─► детект категории            (vision, дешёвая модель)
   │
   ├─► парсинг ТОП-5 конкурентов   (WB API + анализ карточек)
   │        └─► синтез инсайта: чем они одинаковы → где наш разрыв
   │
   ├─► извлечение фактов           (только из брифа и характеристик)
   │        └─► user_facts: набор проверяемых утверждений
   │
   ├─► дизайн-фаза                 (умная модель)
   │        └─► план пака: роль каждой карточки, сцена, копирайт
   │
   ├─► КОД-ГЕЙТЫ ◄── здесь ловится то, что промпт пропустил
   │        ├─ bland_reason()                  — вода и шаблоны
   │        ├─ unverified_number_reason()       — числа не из фактов
   │        ├─ sanitize_description_numbers()   — вычистить выдуманное
   │        └─ card_copy_issues()               — общий вердикт по карточке
   │
   ├─► фаза исправления            (только для карточек, не прошедших гейт)
   │
   ├─► сборка image_prompt         (детерминированно, из кода)
   │
   ├─► рендер изображений          (цепочка провайдеров с фолбэками)
   │
   └─► vision-проверка результата  (текст на картинке отрендерился читаемо?)
```

Ключевая идея: **гейты написаны кодом, а не промптом.** Правило «не выдумывай
числа» в промпте соблюдается «примерно всегда», а в коде — всегда.

---

## Механизмы

### 1. Канал фактов

Числа и характеристики извлекаются из брифа в структуру `user_facts` и дальше
служат белым списком. Любое число в сгенерированном тексте сверяется с ней —
с нормализацией единиц (`мл`/`ml`/`миллилитр` — одно и то же). Не нашлось
в фактах → число вырезается из описания, а карточка уходит на переделку.

Реализация: `extract_facts_from_brief()`, `_facts_numbers()`,
`unverified_number_reason()`, `sanitize_description_numbers()`.

### 2. Детектор воды

Списки шаблонных слов, «пустых» основ и hedge-конструкций плюс требование
сильного триггера (конкретика, цифра, выгода). Заголовок «Качественный товар»
не проходит; «250 мл — как две чашки» проходит.

Реализация: `_BLAND_WHOLE`, `_BLAND_STEMS`, `_STRONG_HOOK_TRIGGERS`,
`bland_reason()`.

### 3. STYLE LOCK

Если пользователь приложил референс стиля, его визуал становится «законом пака»:
единый стиль по всем карточкам, а меняется только кадр и роль. Без этого
пак распадается на набор несвязанных картинок.

### 4. Дифференциация карточек

Роли (`main` / `feature` / `lifestyle` / `comparison`) распределяются
детерминированно, а сцены детальных карточек дедуплицируются кодом — чтобы две
карточки не оказались одним и тем же ракурсом.

### 5. Дисциплина отрицаний

Отдельная обработка фактов-отсутствий («без проводов», «не требует зарядки»),
потому что модели систематически теряют отрицание и превращают его
в противоположное утверждение.

## Маршрутизация моделей: качество там, где оно нужно

Не все шаги одинаково сложные, а стоят они по-разному. Каждой задаче назначен
**тир**, тир мапится на конкретную модель через конфиг:

| Тир | Куда идёт | Почему |
|---|---|---|
| `smart` | дизайн пака, копирайт, правка текста | самое сложное, здесь качество решает |
| `balanced` | синтез конкурентов, описание, вариации | нужен объём, но не пик способностей |
| `vision_cheap` | детект категории, анализ фото | зрение есть, рассуждать не надо |
| `cheap` | уточнение запроса, motion для видео | механические подстановки |

Настраивается через `purpose_tier` в конфиге — см.
[`config.example.json`](../site/config.example.json). Смена модели для целого
класса задач — правка одной строки, без изменения кода.

## Отказоустойчивость

LLM-эндпоинты и генераторы изображений выстроены в **цепочки с фолбэками**:
падение или таймаут одного провайдера переводит запрос на следующего, а не
роняет генерацию. То же самое у парсера WB — несколько независимых источников
данных, от «умного» клиента до публичного поиска.

Реализация: `_chat_resilient()` в `generator.py`, `FALLBACK_CHAINS`,
`wb_parser.py`.
